# 제출 전 검수

아래는 이 스킬에서 사용하는 편집·검수 절차다. 특정 지원 시스템의 자동 심사 통과나 모든 문서에 알맞은 쪽수를 보장하지 않는다.

## 내용 확인

1. 공고의 필수 요건을 다시 읽고, 문서에서 이를 뒷받침하는 경험을 찾는다. 자료로 뒷받침할 수 없는 요건은 사용자 검토 메모에 적는다.
   신규 직무·전문 분야의 목적·책임·판단·산출물을 원문에서 조사했는지 확인한다. 스킬에 사례가 없다는 이유로 미확정 상태나 분류 범위 밖에 두지 않는다. 책임 목록의 누락과 코드 중복을 점검한다. 후보자 정보가 부족하다고 해서 임의로 운영·IT 직무에 배정하지 않는다. 분류 코드와 작업용 속성은 제출본에 자동으로 넣지 않는다.
2. 공식 직함·실제 역할·조직 범위·기간·수치·학위·자격을 근거표와 대조한다. 참여를 총괄로, 수료를 취득으로, 계획을 완료로 바꾸지 않는다.
3. 요약에서 제시한 강점을 본문의 경험이 각각 뒷받침하는지 확인한다. 같은 사례의 상세 설명을 회사별 경력과 성과 절에 두 번 싣지 않는다. 지정 양식에서 두 항목을 모두 요구하면 회사별 경력은 역할을 중심으로 짧게 쓴다.
4. 팀 성과와 본인의 행동이 연결되어 있는지, 인과·기여율·경력 기간을 과장하지 않았는지 확인한다.
   직무별 지표도 대조한다. 계약·인식 매출·수금, 광고에 귀속된 효과·증분 효과, 예산·실적·전망, 처리·재발·품질, 공정·공장의 범위를 서로 혼동하지 않는다. 정기 운영 경험을 억지로 개발 프로젝트로 바꾸지 않는다.
   여러 기능의 책임을 설명하면서 같은 성과를 인용할 때 금액과 개선 효과를 중복 합산하지 않았는지 확인한다.
5. 지원자의 동기·가치관·앞으로의 계획을 요구받으면 지정 문항에 쓰고, 자유 양식에서 기여 방향을 요청받았다면 요약이나 허용된 별도 항목에 반영한다. 확인된 경험, 지원 직무의 과제, 앞으로 맡을 행동이 이어지는지 확인한다. 과거 업무만 허용하는 양식에는 추가하지 않는다. 세 문서를 함께 요청받았다면 문서별 역할을 살리면서 기여 방향이 빠지지 않았는지 대조한다. 이전 회사의 이직 사유나 개인적 깨달음·미래 계획을 이미 달성한 조직 성과로 바꾸지 않는다. 정하지 않은 목표 수치·시한·권한을 만들지 않는다.

## 독자의 ‘왜?’에 답하는지 확인

직무를 모르는 독자의 관점에서 핵심 사례를 읽고, 왜 이 일이 필요했는지, 왜 그 방법·순서·기준을 택했는지, 본인이 실제로 무엇을 판단·실행했는지, 결과가 왜 의미 있는지 답해 본다. 답을 뒷받침하는 문장과 근거를 대조한다. 제목·도구·수치만 있고 연결이 없으면 보완한다.

기존 자료에서 이유를 찾은 뒤에도 확인되지 않은 사실만 질문한다. 외부 직무 조사로 파악한 일반적인 목적을 개인의 실제 판단이나 실현된 성과로 옮기지 않는다. 선택 이유를 설명하려고 자료에 없는 위기·인력 부족·대안 비교를 추가하지 않는다. 목적·계획과 관찰 결과를 구별하고, 문장마다 배경이나 주석을 반복해 읽기 어렵게 만들지 않는다.

## 외부 독자의 개념 이해

내부 프로젝트명·약어·생소한 기술 용어가 설명 없이 남아 있는지 확인한다. 필요한 개념은 공식 공개 자료나 승인된 근거를 실제로 읽고 목적·기능을 설명했는지, 활동 자체와 지원 시스템 및 후보자의 기여를 구별했는지 대조한다. 공개 여부가 불명확한 내부 표현을 검색어나 제출본에 노출하지 않는다. 전문 독자에게 이미 충분한 설명은 반복하지 않는다. 뜻을 확인하지 못한 부분을 추측으로 채우지 않고 작성 가능한 항목을 먼저 완성한다.

## 한국어

- 핵심 책임과 성과를 먼저 쓰고 배경은 이해에 필요한 만큼 붙인다.
- `혁신을 선도`, `탁월한 역량`, `성공적으로 수행` 같은 평가어를 구체적인 행동과 근거로 바꾼다. 실제 평가·수상이 있으면 사실로 보존한다.
- `총괄`, `주도`, `설계`, `구현`, `검토`, `조율`, `기여`는 실제 수행 범위에 맞춰 선택한다.
- 행위자, 지시 대상, 주어와 서술어, 목적어와 동사의 관계를 확인한다. 능동·피동이나 명사형을 일괄 금지하지 않는다.
- 기술명·회사명·직함·수치·기간·조건을 압축 과정에서 바꾸지 않는다. 한국어 문장을 영어식 동사 시작 구조에 억지로 맞추지 않는다.
- 검증된 성과를 반복되는 `단정하지 않습니다`, `미측정`, `기여율 미산출` 같은 해설로 가리지 않는다. 필요한 범위를 본문에 자연스럽게 쓰고 작업상 질문은 문서 밖으로 옮긴다.

## 지정 양식과 파일

1. 제출처의 항목·순서·분량·파일 형식·용량을 우선한다. 이력서와 경력기술서를 하나의 파일로 요구하면 그 조건을 따른다.
   첨부가 필수라는 표시와 파일 형식에 관한 요청·권장을 각각 읽는다. 별표나 업로드 제한이 없어도 설명문에 있는 제출 형식 안내를 보존하고, 권장을 필수로 바꾸지 않는다. 원문의 안내와 시스템이 실제로 허용하는 파일 형식을 혼동하지 않는다. 일부 화면에서 문구를 찾지 못했다면, 기존에 확인한 공고·지원 양식에도 안내가 없다고 판단하지 않는다. 기존 안내의 출처·확인 시점과 이번에 읽은 범위의 한계를 구분해 전달한다.
2. 자유 양식이라면 명확한 제목과 읽기 쉬운 글꼴을 쓰고, 날짜 표기를 통일하며 최근 경력부터 배치한다. 1쪽·2쪽·3쪽을 보편적인 규칙으로 강제하지 않는다.
3. DOCX를 요청받으면 documents, PDF를 요청받으면 pdf 스킬의 생성·렌더링 절차를 적용한다. Markdown 초안만 만들고 DOCX/PDF 검증까지 했다고 보고하지 않는다.
4. 최종 수정 후 모든 쪽의 렌더링 이미지를 확인한다. 제목만 쪽 아래에 남는지, 글자나 표가 잘리는지, 빈 쪽이 생기는지 점검한다. 표 머리행, 줄바꿈, 내용의 밀집도와 링크 표시도 확인한다. 표가 없으면 표 관련 검사를 적용하지 않는다.
5. PDF의 텍스트 추출 순서와 문자 인식을 확인한다. 본문을 이미지로만 넣지 않는다. 구조화된 입력란이 있으면 파일 내용과 기간·직함·수치를 맞춘다. 이 검사를 ATS 호환 인증으로 부르지 않는다.
6. 링크를 넣으면 독자가 연결된 자료에 접근할 수 있는지 확인한다. 접근 문제를 해결하려고 사용자 허가 없이 비공개 자료를 공개하지 않는다. 원문을 확인할 수 없으면 실제로 확인한 범위를 보고한다.

## 전달 순서

완성한 경력기술서를 먼저 전달하고, 필요한 경우 파일 링크를 덧붙인다. 이어서 지원 요건과 경력의 차이, 사실 확인 질문, 수행하지 못한 검증을 짧은 검토 메모로 전달한다. 내부 근거표나 채점표를 자동으로 제출본에 붙이지 않는다. 확인할 질문이 있어도 작성 가능한 부분은 완성한다.
