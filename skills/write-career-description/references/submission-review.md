# 제출 전 검수

아래는 이 스킬의 편집·검수 절차다. 특정 지원 시스템의 자동 심사 통과나 보편적인 최적 쪽수를 보장하지 않는다.

## 내용 확인

1. 공고의 필수 요건을 다시 읽고, 문서에서 이를 뒷받침하는 경험을 찾는다. 자료로 충족하지 못하는 요건은 사용자 검토 메모에 적는다.
   책임 목록에 빠진 항목이 없는지, 분류 완료 항목마다 주분류가 하나인지 확인한다. 정보 부족·범위 밖을 임의의 운영·IT 직무로 넣지 않는다. 분류 코드와 작업용 속성은 제출본에 자동으로 노출하지 않는다.
2. 공식 직함·실제 역할·조직 범위·기간·수치·학위·자격을 근거표와 대조한다. 참여를 총괄로, 수료를 취득으로, 계획을 완료로 바꾸지 않는다.
3. 요약의 강점마다 본문 근거가 있는지 확인한다. 같은 사례의 상세 설명을 회사별 경력과 성과 절에 두 번 싣지 않는다. 지정 양식이 둘 다 요구하면 회사별 경력은 역할 중심으로 짧게 쓴다.
4. 팀 결과에 본인의 행동이 연결되어 있는지, 인과·기여율·경력 기간이 과장되지 않았는지 확인한다.
   직무별 지표도 대조한다. 계약·인식 매출·수금, 광고 귀속·증분 효과, 예산·실적·전망, 처리·재발·품질, 공정·공장 범위를 섞지 않는다. 정기 운영 경험을 억지로 개발 프로젝트로 바꾸지 않는다.
   여러 기능으로 나눈 책임이 같은 성과를 인용할 때 금액·개선 효과가 중복 합산되지 않았는지 확인한다.
5. 지원자의 동기·가치관·앞으로의 계획을 요구받은 경우 별도 문항에 쓴다. 이전 회사의 이직 사유나 개인적 깨달음을 이미 달성한 조직 성과로 만들지 않는다.

## 한국어

- 핵심 책임과 성과를 먼저 쓰고 배경은 이해에 필요한 만큼 붙인다.
- `혁신을 선도`, `탁월한 역량`, `성공적으로 수행` 같은 평가어를 구체적인 행동과 근거로 바꾼다. 실제 평가·수상이 있으면 사실로 보존한다.
- `총괄`, `주도`, `설계`, `구현`, `검토`, `조율`, `기여`는 실제 수행 범위에 맞춰 선택한다.
- 행위자, 지시 대상, 주어와 서술어, 목적어와 동사의 관계를 확인한다. 능동·피동이나 명사형을 일괄 금지하지 않는다.
- 기술명·회사명·직함·수치·기간·조건을 압축 과정에서 바꾸지 않는다. 한국어 문장을 영어식 동사 시작 구조에 억지로 맞추지 않는다.
- 검증된 성과를 반복되는 `단정하지 않습니다`, `미측정`, `기여율 미산출` 같은 해설로 가리지 않는다. 필요한 범위를 본문에 자연스럽게 쓰고 작업상 질문은 문서 밖으로 옮긴다.

## 지정 양식과 파일

1. 제출처의 항목·순서·분량·파일 형식·용량을 우선한다. 이력서와 경력기술서를 하나의 파일로 요구하면 그 조건을 따른다.
2. 자유 양식이라면 명확한 제목, 읽기 쉬운 글꼴, 일관된 날짜와 역순 경력을 기본으로 선택한다. 1쪽·2쪽·3쪽을 보편적 규칙으로 강제하지 않는다.
3. DOCX를 요청받으면 documents, PDF를 요청받으면 pdf 스킬의 생성·렌더링 절차를 적용한다. Markdown 초안만 만들고 DOCX/PDF 검증까지 했다고 보고하지 않는다.
4. 최종 수정 후 모든 쪽의 실제 렌더 이미지를 확인한다. 제목 고립, 글자·표 잘림, 빈 쪽, 표 머리행, 줄바꿈, 밀집, 링크 표시를 점검한다. 표가 없으면 표 관련 검사를 적용하지 않는다.
5. PDF의 텍스트 추출 순서와 문자 인식을 확인한다. 본문을 이미지로만 넣지 않는다. 구조화된 입력란이 있으면 파일 내용과 기간·직함·수치를 맞춘다. 이 검사를 ATS 호환 인증으로 부르지 않는다.
6. 링크를 넣으면 접근 가능한 범위인지 확인한다. 접근 문제를 해결하려고 사용자 허가 없이 비공개 자료를 공개하지 않는다. 원문을 확인할 수 없으면 확인한 범위를 보고한다.

## 전달 순서

완성 경력기술서 → 필요한 경우 파일 링크 → 지원 요건 차이·사실 확인 질문·미실시 검증을 담은 짧은 검토 메모 순서로 전달한다. 내부 근거표나 채점표를 자동으로 제출본에 붙이지 않는다. 질문이 있어도 작성 가능한 부분을 완성한다.
