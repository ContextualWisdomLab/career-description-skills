## 1. 조사 범위

국내 IT·개발·데이터·AI·AX와 관련 운영 리더의 공개 공고, 공식 경력 작성 지침, 관리자 역할 정의를 선별했다. 채용 공고의 요구사항을 조사한 것으로 실제 합격자의 서류나 채용 결과 연구가 아니다. 표본은 목적에 맞춰 선택했으며 채용시장 전체를 대표하지 않는다.

모든 아래 출처의 확인일은 2026-11-08이다. 정확한 게시·마감일이 본문에 없으면 미표시로 기록했다. 검색엔진의 크롤링 날짜를 게시일로 바꾸지 않았다. 지원 링크의 존재는 접수 성공이나 잔여 채용 인원을 검증한 것이 아니다. 공고를 실제 지원에 사용할 때는 최신 원문과 제출 조건을 다시 확인한다.

## 2. 채용 사례와 확인 범위

H01~H04는 기업 채용사이트 상세 원문을 확인했다. H05는 원티드 게재 공고, H06은 기업의 공고 목록과 고용24에 연계된 원티드 본문을 확인했다. 기업 원문과 플랫폼 게재 자료의 확인 수준을 구분한다. 여섯 사례 중 네 건이 토스 계열사이므로 금융·보안 직무 쪽으로 표본이 치우쳐 있다.

## 3. 공식 작성 지침과 역할 정의

### G01. Toss — Joining the Toss Community / 토스커뮤니티 합류 여정

- [공식 안내](https://toss.im/career/joining-guide)
- 발행·수정일: 본문 미표시. 확인 위치: Apply to Toss / 지원서 작성하기.
- **확인한 권고**: 경험에서의 영향과 배움, 직무별 작성 지침을 강조한다. 개발 직군의 기술 스택, PDF 변환을 안내하며 주민등록번호·주소·현재 연봉은 필수가 아니라고 설명한다.
- **적용 범위**: 해당 기업의 지원 안내다. PDF를 모든 기업의 공통 필수 형식으로 일반화하지 않는다.

### G02. MIT CAPD — Resumes: Writing about your skills

- [공식 안내](https://capd.mit.edu/resources/resumes-writing-about-your-skills/)
- 발행·수정일: 확인한 본문 미표시. 확인 위치: PAR Statements, Using numbers to show impact, How to best represent your experiences.
- **확인한 권고**: 프로젝트·과제, 본인의 행동, 결과를 연결한다. 수치는 결과뿐 아니라 업무 규모도 보여 준다. 지원 역할과 관련된 경험을 읽기 쉽게 배치한다.
- **적용 범위**: 대학의 영문 이력서 교육 자료다. 영어의 동사 시작 문장이나 학생용 예시·분량을 한국어 경력기술서에 그대로 강제하지 않는다. 예시의 인물·성과 수치는 재사용하지 않는다.

### G03. MIT CAPD — Make your resume* ATS-friendly

- [공식 안내](https://capd.mit.edu/resources/make-your-resume-ats-friendly/)
- 발행·수정일: 확인한 본문 미표시. 확인 위치: Format for the ATS, supported file type, Test your resume beforehand.
- **확인한 권고**: 이미지·복잡한 표·텍스트박스·열 구성은 파싱 과정에서 내용이나 순서를 흐트러뜨릴 수 있다. 요청한 파일 형식을 따르고 텍스트로 변환해 누락·읽기 순서를 점검한다. 공고 용어는 실제 경험에 맞게 사용한다.
- **적용 범위**: 파싱 위험을 줄이는 실무 권고다. 단순 레이아웃은 이 스킬의 기본 선택이며 모든 ATS의 지원 여부나 채용 통과를 인증하지 않는다. 기업 지정 표 양식을 임의로 없애지 않는다.

### G04. GitLab — Engineering Manager

- [공식 역할 정의](https://handbook.gitlab.com/job-description-library/engineering/development/management/engineering-manager/)
- 원문 표시 최종 수정일: **2026-10-30**. 본문 내용의 최초 작성일은 확인하지 않았다.
- 확인 위치: 역할 소개, Responsibilities, Performance Indicators.
- **확인한 역할**: 구성원 성장·피드백·채용, 팀의 결과 책임, 부서 간 조율, 기술적 결정 지원, 품질·보안·가용성을 다룬다. 관리자의 성과 지표는 대체로 본인과 직속 구성원을 포함하는 팀에 적용된다.
- **적용 범위**: 현재 모집 공고가 아닌 GitLab의 직무 정의다. 다른 회사 팀장의 인사권·보고 관계를 추정하는 근거로 쓰지 않는다.

- [공식 역할 정의](https://handbook.gitlab.com/handbook/engineering/careers/ic-leadership/tech-lead/)
- 원문 표시 최종 수정일: **2026-03-19**. 본문 내용의 최초 작성일은 확인하지 않았다.

## 5. 스킬 설계에 반영한 판단과 한계

| 스킬의 판단 | 근거·성격 |
| --- | --- |
| 실제 공고와 제출 조건부터 확인 | H01~H06의 개별 요건과 확인 수준, G01·G03의 기관 안내 |
| 팀 책임·개인 행동·결과를 연결 | H02~H04의 작성 권고, G02·G04를 적용한 편집 설계 |
| 사람관리·기술 리딩·프로젝트 조율을 구분 | G04·G05의 역할 차이를 참고한 사실 확인 절차 |
| 중복 경력은 합집합으로 계산 | K01 및 이 스킬의 데이터 처리 규칙; 보편적인 법적 경력 인정 기준이 아님 |
| 수치의 분모·기간·단위·실현 여부를 확인 | 사실 보존과 산술 검증 절차; 특정 채용기관의 점수식이 아님 |
| AX의 업무 대기·판단 기준·현업 정착을 확인 | H05를 참고해 업무 변화의 책임과 결과를 구체화한 직무별 편집 판단 |
| 조직 운영과 사업 지표를 함께 확인 | H01·H06의 예산·운영·조율 책임을 참고한 편집 판단 |
| 근거표와 제출용 본문을 나눔 | K01 및 이 스킬의 문서 설계 |
